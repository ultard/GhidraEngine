# Бенчмарки

Измеряются две стадии, которые определяют время скана: декодирование JPEG (упирается в него
пропускная способность по фото) и запрос к MIH-индексу (решает, масштабируется ли библиотека
дальше нескольких десятков тысяч файлов). Плюс ядра DCT — ради проверки, что SIMD
действительно окупается.

## Запуск

Бенчмарки не входят в обычную сборку (`GHIDRAENGINE_BUILD_BENCHMARKS=OFF`), для них есть
отдельные пресеты:

```powershell
cmake --preset windows-bench
cmake --build --preset windows-bench
.\build\windows-bench\bench\ghidraengine_bench.exe
```

```bash
cmake --preset linux-bench   # или macos-bench
cmake --build --preset linux-bench
./build/linux-bench/bench/ghidraengine_bench
```

Полезные флаги Google Benchmark:

```bash
ghidraengine_bench --benchmark_filter=Mih          # только индекс
ghidraengine_bench --benchmark_repetitions=5       # со статистикой по повторам
ghidraengine_bench --benchmark_out=bench.json --benchmark_out_format=json
```

Внешние файлы не нужны: тестовые изображения генерируются детерминированно
(`tests/image_fixture.cpp`) и кодируются в JPEG один раз на размер, поэтому кодирование не
попадает в измерение.

## Что измеряет каждый бенчмарк

| Бенчмарк | Что показывает |
|---|---|
| `BM_Dct16Scalar` | скалярная 32×32 → 16×16 DCT, точка отсчёта |
| `BM_Dct16Dispatched` | то же ядро, выбранное в рантайме; в подписи строки — активный бэкенд |
| `BM_DecodeJpeg/W/H` | быстрый путь: декод из DCT-коэффициентов сразу в 1/8 |
| `BM_DecodeJpegFullResolution/W/H` | тот же файл целиком, как это сделал бы обычный загрузчик |
| `BM_SignaturePipeline` | декод + все четыре хеша — стоимость одного фото целиком |
| `BM_SignatureDihedral` | надбавка за `dihedral_invariant` (декод исключён) |
| `BM_MihBuild/N` | построение индекса на N кодов |
| `BM_MihQuery/N` | один запрос с порогом 10 бит |
| `BM_LinearScanQuery/N` | тот же запрос полным перебором |

## Результаты

24 потока @ 3.7 ГГц, MSVC 19.44, RelWithDebInfo.

Декод JPEG, 1/8 против полного разрешения:

| Разрешение | Fast path | Полный декод | Выигрыш |
|---|---|---|---|
| 1920×1080 | 1.11 мс | 3.93 мс | 3.5× |
| 4000×3000 | 5.60 мс | 20.7 мс | 3.7× |
| 6000×4000 | 10.6 мс | 40.2 мс | 3.8× |

Поиск, MIH против линейного скана (порог 10 бит, один запрос):

| Корпус | MIH | Линейный | Выигрыш |
|---|---|---|---|
| 10 000 | 1.5 мкс | 14.7 мкс | 10× |
| 100 000 | 5.5 мкс | 147 мкс | 27× |
| 1 000 000 | 39.8 мкс | 1467 мкс | 37× |

- DCT 32×32 → 16×16: 557 нс на AVX2 против 2566 нс скалярно — 4.6×.
- Все четыре хеша поверх декода 4000×3000: +30 мкс к 5.60 мс — 0.5%.
- Повторный скан по кешу: 3.6 мс против 37 мс, ноль прочитанных байт.

Числа зависят от машины; смысл таблиц не в абсолютных значениях, а в соотношениях.
Проверить свою систему: `--benchmark_filter=DecodeJpeg` и `--benchmark_filter=Query`.

## Чего бенчмарки не измеряют

Обход файловой системы, диск и SQLite. Они целиком определяются носителем и кешем ОС, и
микробенчмарк на них измеряет не библиотеку, а машину. Для сквозной картины считайте время
на реальном дереве: `ghidraengine --cache -q D:/Photos` и поле `elapsed_seconds` в
`-f json`.
